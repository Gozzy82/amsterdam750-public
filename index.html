01 / Aanleiding

Van frustratie naar een toetsbare hypothese.

Bij de ticketuitgifte voor festival Op de Ring stonden mensen uren in een digitale wachtrij. Wie uiteindelijk binnenkwam, kon alsnog foutmeldingen krijgen; in enkele gevallen konden tickets opnieuw worden besteld zonder opnieuw aan te sluiten.

Mijn hypothese: voor een pre-registratie hoeft een browser geen uren een plek in de rij vast te houden. Laat iemand zijn belangstelling snel en veilig vastleggen, verwerk de piek serverless en handel uitnodigingen daarna asynchroon af.

De publieke aanleiding

“Mensen die urenlang in de wachtrij hebben gestaan, lukt het maar niet om tickets te krijgen.”

NOS, 20 mei 2025 ↗

Bewuste scope: dit is geen kopie van de volledige originele ticketketen. Ik isoleerde het registratieprobleem om mijn alternatief eerlijk te kunnen testen.

02 / Frontend

Terug naar het begin.
Maar niet terug in de tijd.

Mijn frontendloopbaan liep van vanilla JavaScript via Ext JS naar React en TypeScript. HTMX voelt als terugkeren naar de basis - met twintig jaar extra inzicht in wanneer complexiteit wel en niet iets oplevert.

  1. 01

    Vanilla JavaScript

    Hier leerde ik wat de browser zelf kan: events, formulieren, het DOM en HTTP. Die basis is nooit verdwenen.

  2. 02

    Ext JS

    Voor grote bedrijfsapplicaties bracht Ext JS structuur en herbruikbare componenten, maar ook een zwaar frameworkmodel.

  3. 03

    React + TypeScript

    React was de juiste stap voor rijke interfaces met veel client-state. Ik moderniseerde er jarenlang complexe software mee.

  4. 04

    HTMX

    Nu kies ik voor servergestuurde HTML wanneer de interactie vooral uit formulieren en navigatie bestaat. Minder JavaScript, minder state, minder bewegende delen.

De volwassen keuze is niet voor of tegen een framework. Het is weten hoeveel framework een probleem werkelijk nodig heeft.

03 / Security

Encryptie is geen vinkje. Het is één laag in een systeem.

De Odido-inbraak laat zien hoeveel blijvende schade ontstaat wanneer één toegangspad een grote verzameling persoonsgegevens blootlegt.

In februari 2026 verkregen aanvallers via geraffineerde voice phishing toegang tot een klantcontactsysteem. Gegevens uit meer dan zes miljoen accounts werden gestolen, waaronder namen, e-mailadressen, telefoonnummers, IBANs, geboortedata en identificatiegegevens.

De les die ik toepas

Ga ervan uit dat één verdedigingslaag ooit faalt.

Encryptie van opgeslagen data helpt wanneer storage of een back-up wordt buitgemaakt. Ze helpt niet automatisch wanneer een aanvaller via een legitiem applicatiepad leesrechten verkrijgt. Daarom combineer ik cryptografie met minimale gegevensopslag, gescheiden identiteiten, least privilege, anti-abuse en auditability.

Odido: verloop van de aanval ↗ Reuters: omvang en datatypes ↗
01

Minimaliseren & scheiden

Alleen noodzakelijke PII wordt opgeslagen. De publieke registratieflow en de administratieve decryptieflow draaien in afzonderlijke Function Apps.

02

Versleutelen in de applicatie

PII wordt voor opslag versleuteld met AES-256-GCM, een willekeurige DEK en IV, plus AAD die de ciphertext aan het record bindt.

03

Sleutels buiten de data

Iedere DEK wordt gewrapt met een Key Encryption Key in Azure Key Vault. Managed Identity en RBAC bepalen welke component mag decrypten.

04

Misbruik & impact begrenzen

Turnstile, rate limiting, gehashte uniqueness-locks, optimistic concurrency, audit logging en monitoring vormen extra verdedigingslagen.

Envelope encryption
PII → AES-256-GCM → encrypted record DEK → RSA-OAEP-256 → wrapped key

De data en de sleutel die haar leesbaar maakt, volgen bewust verschillende beveiligingspaden.

04 / Architectuur

De browser doet browserwerk. Azure doet schaalwerk.

De gebruiker krijgt direct een gewone HTML-respons. De piek wordt serverless opgevangen; uitnodigingen en verificatie lopen daarna gecontroleerd verder.

01

Browser + HTMX

Native formulier, validatie en toegankelijke HTML-responses.

02

Public Function

Valideert, begrenst misbruik en normaliseert invoer.

03

Table + Key Vault

Slaat versleutelde PII en gescheiden sleutelmateriaal op.

04

Queue + Worker

Verwerkt uitnodigingen buiten de piek en onafhankelijk van de browser.

05

E-mail + SMS

Verstuurt uitnodigingen en verifieert het telefoonnummer via OTP.

Progressive enhancement

HTML over the wire, precies waar dat genoeg is.

De pre-registratie is een formulierflow, geen desktopapplicatie in een tabblad. HTMX laat de server aangeven welk HTML-fragment moet worden vervangen. De browser behoudt zijn eigen sterke punten: semantiek, formulieren, focus, geschiedenis en toegankelijkheid.

<form hx-ext="json-enc" hx-swap="none">
Wat gebeurt er na ‘Versturen’?
  1. De browser valideert de invoer en HTMX verstuurt het formulier.
  2. De Function controleert Turnstile, rate limits en de genormaliseerde waarden.
  3. PII wordt lokaal versleuteld; gehashte locks voorkomen dubbele registraties.
  4. De server stuurt een klein HTML-resultaat terug naar het juiste element.
Waarom een queue?

Een registratiepiek en het versturen van uitnodigingen hebben een ander tempo. Queue Storage ontkoppelt die twee, zodat bezoekers niet wachten op downstream werk.

Waarom React hier niet nodig was?

Deze flow heeft weinig langdurige client-state. React zou kunnen werken, maar voegt hier meer state- en buildcomplexiteit toe dan het probleem vraagt. Deze portfoliosite is daarom zelf ook statische HTML en CSS, zonder React-runtime.

05 / Van code naar bewijs

Resultaten zijn pas bewijs als de methode controleerbaar is.

Scope

Wat de cijfers wel zeggen

De genoemde cijfers beschrijven één Azure Load Testing-run met 250 virtuele gebruikers tegen de pre-registratieflow: 126.124 succesvolle POST-registraties, geen mislukte requests en een uit de ruwe resultaten berekende p95 van 634 ms.

Grenzen

Wat de cijfers niet bewijzen

Eén run bewijst geen onbeperkte schaalbaarheid, foutloos productiegedrag of gelijkwaardige resultaten in iedere regio en configuratie. Resultaten zijn afhankelijk van testdata, infrastructuur, warming en meetdefinities.

Methode

Reproduceerbare beschrijving

Scenario, meetdefinities, acceptatiecriteria en ontbrekende context zijn vastgelegd in de loadtestmethodologie. Daar zijn ook de originele inputbestanden, resultaten en logs met SHA-256-checksums te downloaden.
