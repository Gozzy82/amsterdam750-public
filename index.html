Engineering case study · Azure · 2026

Designing a simpler registration flow for very high demand.

I designed and built a serverless pre-registration platform with Azure Functions, Table Storage, Key Vault, HTMX and TypeScript. The goal was not to reproduce an existing ticketing system, but to test whether a narrower registration problem could be made simpler, safer and easier to scale.

01 · Problem

Reduce the synchronous work before trying to scale it.

The public Amsterdam 750 ticket release showed a familiar failure mode: large numbers of visitors waiting for access to a scarce downstream process. I used that situation as a starting point for a smaller engineering question.

What if pre-registration itself were a short, stateless operation? Instead of keeping a browser tied to a long-running queue, capture intent quickly, protect the data immediately, and move follow-up work out of the request path.

This case study deliberately isolates that registration problem. It is not a claim that the complete original ticketing chain can be replaced by this architecture.

02 · Design

Keep the browser simple and move elasticity into Azure.

01

Browser + HTMX

Native forms and server-returned HTML, with very little long-lived client state.

02

Public Function

Validation, anti-abuse checks, normalization and registration handling.

03

Table Storage

Encrypted records, hashed uniqueness controls and optimistic concurrency.

04

Key Vault

Key-encryption operations are separated from the data itself.

05

Queue + worker

Invitations and follow-up work are processed independently from the initial request.

The design choice I care about most is not “HTMX instead of React” or “serverless instead of servers”. It is matching the amount of system complexity to the actual problem.
03 · Security

PII protection is a system property, not an encryption checkbox.

Application-level encryption

Stored PII is encrypted with AES-256-GCM before it reaches storage.

Per-record data keys

Each data-encryption key is wrapped with a Key Encryption Key held in Azure Key Vault.

Separated privileges

Public registration and privileged administration/decryption responsibilities are split.

Defense in depth

Rate limits, anti-abuse controls, hashed uniqueness locks, RBAC, monitoring and data minimisation reduce impact when one layer fails.

Important limitation: encryption at rest does not help if an attacker gains a legitimate application path that is allowed to decrypt the data. The architecture therefore treats encryption as one boundary among several.
